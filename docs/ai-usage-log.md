## 5.2 AI 使用说明

### AI 帮了什么

1. **把需求翻译成结构**：作业文档是一段段自然语言，AI 把它拆成了「集合 / 索引 / 接口 / 页面 / 用例」这些可执行单元，省掉了大量梳理时间。
2. **写模板化的重复代码**：模型定义、CRUD 路由、错误处理、页面骨架、测试的 setup/teardown 这些高度重复的部分，AI 一次生成的可用率很高。
3. **提供多个备选方案**：例如「答卷要不要拆表」「过期要不要写进状态」，AI 都给了两个方向，我只需要判断取舍——**判断仍然由我做**（见下）。
4. **写文档初稿**：设计说明、API 文档这种「结构清晰但篇幅长」的内容，AI 起草后人工核对字段，效率明显高于从零写。

### AI 做错了什么

| 错误 | 表现 | 为什么错 | 怎么发现 |
| --- | --- | --- | --- |
| 题目内嵌在问卷里 | 初版 schema 把题目做成数组 | 忽略了「编辑期只改一道题」的写放大和并发覆盖问题 | 手写「两个标签页同时改不同题」的场景时推演出来 |
| 用三个布尔表示问卷状态 | `is_published` / `is_closed` / `is_expired` | 布尔组合会产生非法状态，且「过期」不是被写入的状态 | 画状态转移图时发现 8 种组合里有 4 种非法 |
| 跳转引擎只认 `_id` | 服务端测试全过，前端跳转失效 | 服务端是 Mongoose 文档（有 `_id`），浏览器拿到的是接口 DTO（只有 `id`），AI 只考虑了其中一侧 | 用 jsdom 真实执行填写页，点「学生」后仍显示第 2 题 |
| 排序一次写好新题号 | 调整顺序接口返回 409 | 忽略了 `{survey_id, order}` 唯一索引在批量更新时的中间态冲突 | 测试用例 T30b 直接失败 |
| 删除题目只重排题号 | 库里残留指向已删题的跳转规则 | 只看到了主流程，没考虑引用完整性 | 写「删除后检查规则」的用例时暴露 |
| 统计占比用总答卷数做分母 | 有跳转时占比之和远小于 100% | 没有意识到「跳过某题」会让该题的作答人数小于总答卷数 | 用跳转问卷造数据时发现 |
| 文本长度用 `str.length` | 1 个 emoji 被算成 2 个字 | 不熟悉 JS 字符串是 UTF-16 码元序列 | 专门写 emoji 用例时暴露 |

### 自己改了什么

- **数据结构**：题目从内嵌改为独立集合；状态从三个布尔改为单枚举 + 独立 deadline；答卷增加 `schema_version` 与 `path`（作答路径快照）。
- **规则引擎**：加「只允许向后跳」「步数上限」两道防死循环；把 `_id`/`id` 统一成 `qid()`；改为前后端共用（UMD）。
- **写入路径**：题目排序改两阶段更新；删除题目补上死规则清理与重排；题目增删同步维护 `question_count`。
- **统计口径**：分母改为「答过该题的人数」，并额外返回 `response_rate`。
- **校验细节**：文本按码点计长、多选去重、数字非法值显式报错。
- **前端交互**：文本/数字改用 `input` 事件记录答案；填写页只提交答案、由服务端重算路径。

### 自己设计了什么

以下部分是我自己定的方案，AI 只负责实现或根本没参与：

1. **「一次提交 = 一个文档」的取舍原则**：用单文档原子性替代多文档事务，并用「单卷题数 ≤ 200、文本有长度上限」把文档体积控制在安全范围。
2. **发布后冻结题目结构**：`draft → published → closed` 单向状态机。这条规则是我加的，因为它能一次性消除「历史答卷无法解释」的一整类问题；也正好给第二阶段留出「不能推倒重做、只能在原结构上扩展」的演进空间。
3. **路径由服务端权威重算**：前端只提交答案，不提交路径。这样即使有人改前端、绕过界面，也绕不过必答题与跳转一致性。
4. **「规则是数据」的建模方式**：把跳转抽象成 `when.op` + `target`，引擎只解释不判断。新增一种条件只需加一个 `op` 分支，不用改数据结构——这是为第二阶段的需求变更预留的。
5. **前后端共用引擎的工程方案**：UMD 包装 + Express 静态托管 `/core`，让「一份规则、两处执行」在零构建工具的前提下成立。

## 5.3 对话节选

以下三段对话**真实发生过**，按原样节选（省略号处为与主题无关的轮次）。每段对话对应一个「AI 初稿有问题 → 由我发现并推动修正」的过程，与日志表中的条目一一对应。

### 对话 1：测试断言写错（对应日志 #16）

> **我**：跑一下新用例，T61 挂了，看看为什么。
>
> **AI**：T61 失败原因是断言路径不对。测试里写的是 `bad.body.errors.flatMap(...)`，但接口实际返回的结构是：
> ```json
> { "error": { "details": { "errors": [ ... ] } } }
> ```
> 改成 `bad.body.error.details.errors.flatMap((e) => e.messages)` 即可。
>
> **我**：为什么你第一次写测试时没按这个结构写？项目里其他用例都是这么断言的。
>
> **AI**：这是我的失误。我按「常见的扁平 errors 数组」惯例写了断言，而没有先查看项目里 `utils/errors.js` 的统一错误封装。已确认其余 9 条新用例的断言均与实际响应结构一致。
>
> **我**：以后生成测试前先读一个既有用例对齐约定，再写。

### 对话 2：复制问卷的跳转规则（对应日志 #15）

> **我**：复制问卷接口写完了？我复制了一份有跳转的问卷，发布后填写，跳转跳回了**原来的问卷**的题目，前端找不到题。
>
> **AI**：抱歉，`/duplicate` 里我用 `{ ...r.toObject() }` 原样复制了 `jump_rules`，`target_question_id` 还指向原问卷的题目。需要先创建全部题目拿到新 id，再按映射重写：
> ```js
> const idMap = new Map(srcQuestions.map((q, i) => [String(q._id), created[i]._id]));
> rules = rules.map((r) => ({ ...r, target_question_id: idMap.get(String(r.target_question_id)) }))
>              .filter((r) => r.to === 'end' || r.target_question_id);
> ```
>
> **我**：映射要放循环里逐题 set，不能一次 build——你第二次循环里 `created[i]` 和 `srcQuestions[i]` 顺序是对的吗？
>
> **AI**：是的，两者都按 `order` 排序后一一对应。另外我加了 `filter`：如果目标题没被复制到（理论上不会发生），这条规则会被丢弃而不是留下 `target: null` 的死规则。
>
> **我**：好。这个场景必须有一条专门用例（T64），断言复制后规则指向**副本**的题目 id。

### 对话 3：截图脚本静默失败（对应日志 #19 的 UI 验证环节）

> **我**：用 Edge 无头模式截页面图，命令退出码是 0，但截图文件时间戳没变——根本没写文件。也没有任何报错。
>
> **AI**：这是 Edge 155 的已知行为变化：`--headless=new` 模式参数被移除后，旧参数写法会**静默失败**而不是报错。改用 `--headless`。另外每次截图前先 `taskkill` 掉残留进程并等 3 秒，避免 user-data-dir 被锁。
>
> **我**：改了还是偶发不写文件。
>
> **AI**：两个叠加因素：① 上一进程尚未完全退出就启动新的，会静默退出；② 登录态通过 `set-token.html?t=…&next=…` 中转页注入，跳转后的页面还没渲染完就截图，会截到半透明动画帧。建议加 `--virtual-time-budget=6000` 让虚拟时间跑完动画再截。实测仍有「第一次调用必失败」的现象，重试一次即可成功——原因未完全定位，已在脚本里按「失败重试一次」处理。

### 对话 4：需求变更的数据结构决策（对应日志 #21）

> **我**：八条需求里最要紧的是「改题不能影响已做好的问卷」。题库题是不是让问卷直接引用，然后跟着最新版走？
>
> **AI**：可以让问卷题存 `bank_question_id` 引用题库文档，读取时 join 最新版本。这样选题复用最直接。
>
> **我**：不行，这正好违反第三条——老师改了题，去年发布的问卷内容就变了，收集的数据全对不上。
>
> **AI**：那就反过来：选题时把题目内容**整体拷贝**进问卷（快照），`bank_question_id` 只记来源用于反查和统计。题库题修改永远生成新版本不覆盖。这样第三条自动满足，第五条「不同问卷用不同版本」也自动成立——各自引用不同版本文档即可。
>
> **我**：这个方向对。版本链用数组存还是独立文档？
>
> **AI**：建议独立文档（版本即文档）：数组方案随修改次数无限膨胀且并发互覆；独立文档 `{root_id, version, parent_id}` 天然成链，「恢复旧版本」就是以旧内容再追加一个新版本，历史一条不删。

### 对话 5：root_id required 引发的 400（对应日志 #22）

> **我**：创建题库题一直 400，`details: ["root_id"]`，可我明明在 save 前回填了。
>
> **AI**：`Model.create()` 在**插入那一刻**就跑 schema 校验，此时 `root_id` 还是 `null`（required 校验失败），根本轮不到你后面的回填。把 `required: true` 去掉，回填改由写路径约定保证——v1 的根是自身，这条约定已经在所有创建入口实现了。
>
> **我**：去掉后 T70 过了，但「只改题干」的用例又 400。
>
> **AI**：修改接口调了 `buildQuestionPayload(body)`，只传 `{title}` 时 options 是 undefined，「选项必须是数组」直接抛错。改成部分更新语义：未传字段从当前版本继承，等价于「改什么补什么，其余不动」。

## 5.4 提示词示例

以下是几条真实使用的提示词（原文摘录）：

> **示例 1（数据库设计）**
> 设计问卷系统的 MongoDB schema：用户、问卷、题目、答卷。要求：说明每个集合为什么这么拆、给出索引及理由、说明为什么不用关系模型。题目要支持单选/多选/文本/数字四种题型，每种题型有不同的约束字段。

> **示例 2（跳转引擎）**
> 写一个跳转引擎：每道题可能有若干条 jump_rules，条件可以是「选了某个选项」「数值大于等于」「文本包含关键字」，动作可以是「跳到某道题」或「结束问卷」。给定题目列表和答案，返回实际作答路径。要求：规则不能写死在代码里；必须防止死循环。

> **示例 3（发现 bug 后的修复请求）**
> 前端填写页选「学生」后没有跳到第 4 题，而是走到了第 2 题。后端同样的规则用测试跑是通的。帮我定位为什么同一份引擎在前端不生效。

> **示例 4（测试）**
> 写自动化测试，覆盖：创建问卷、添加题目、跳转逻辑、校验（必答/多选数量/文本长度/数字范围）、提交问卷、统计。用 node:test + supertest，连真实 MongoDB，每个测试文件用独立数据库。

## 5.5 一点总结

AI 在这个项目里承担的是「写代码的人」，我承担的是「做决定的人」。凡是涉及**数据怎么放、状态怎么流转、一致性怎么保证**的地方，AI 的初稿几乎都需要修改——它能写出能跑的代码，但不承担设计后果。真正花时间的不是让它写，而是判断它写的对不对：92 个测试用例里有 5 个（T30b、T10 前端、T23 分母）正是用来抓这些「看起来能跑但设计错了」的问题。

## 5.6 多用户可用性审计（交付后补做）

### 审计方法

不是「读一遍代码」，而是代入三个角色走查：

1. **第二个注册的用户**：登录后看到什么？空状态有没有引导？能不能碰到别人的数据？
2. **被共享题目的同事**：能做什么、不该看到什么？
3. **手滑的用户**：地址栏少个参数、id 被改坏、问卷超过一页，会发生什么？

### 修复清单

| # | 问题 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | `dashboard.html` 使用了 `toast(...)` 但解构时漏了 `toast` | 复制问卷成功后抛 `ReferenceError`，列表不刷新；导出 CSV 成功后弹「toast is not defined」 | 补进解构列表 |
| 2 | 路径参数非 ObjectId 时 Mongoose 抛 `CastError` | 直接 500「服务器内部错误」，用户看不懂 | 全局错误处理把 `CastError` 转成 400 `BAD_REQUEST` |
| 3 | 题库 `usage` / `stats` 对被共享者开放 | 共享一次题，就能看到对方问卷标题与跨问卷汇总的答卷内容 | 收敛为仅出题人（403），前端对被共享题隐藏这两个按钮 |
| 4 | 修改题库题时顺手改了旧版本的 `updated_at` | 版本历史不再只读，「历史记录」语义被破坏 | 去掉对旧文档的写入，只追加新版本 |
| 5 | `index.html` 对 `next` 二次 `decodeURIComponent` | 路径含 `%` 时可能解码错乱甚至抛异常；且 `next=//evil.com` 可跳站外 | URLSearchParams 已解码，去掉二次解码；只接受单个 `/` 开头的站内路径 |
| 6 | 问卷列表固定 `size=50`，无翻页 | 超过 50 份问卷后，更早的问卷彻底看不到 | 后端保持分页能力，前端补上一页/下一页与页码 |
| 7 | 题库「修改（新版本）」只能改题干 | 想改选项/题型只能重新建题，版本能力形同虚设 | 改为完整编辑弹窗（题型/题干/选项/必答），保存即生成新版本 |
| 8 | 已关闭问卷仍显示可点的「保存设置」 | 点了必然 409，属于无效操作 | 关闭后禁用截止时间与保存按钮 |
| 9 | 统计明细里显示受访者的数据库 ObjectId | 对使用者没有意义，还暴露内部主键 | 改为「登录用户填写 / 匿名填写」 |
| 10 | 反向代理部署时 `share_url` 固定 http | https 站点复制出的填写链接协议错，扫码打不开 | `trust proxy` + `X-Forwarded-Proto`；另补三条基础安全响应头 |
| 11 | 已发布问卷的题目列表仍显示「添加题目」「从题库选题」 | 用户填完题目表单提交必然 409，白做一遍 | 发布后隐藏这两个入口；后端 `assertDraft` 仍作最终防线 |

### 回归用例

新增 T89~T92，锁住其中 4 个最容易被改回去的行为（共享边界、历史不可变、非法 id 400、选题参数校验），全套测试从 88 条增加到 **92 条**。

### 额外做的双账号验收

除了自动化测试，另起一个独立数据库与端口，用两个真实账号把「注册 → 建卷 → 加题 → 存题库 → 共享 → 对方选题 → 改题不影响快照 → 双方分别发布 → 匿名与登录各填一份 → 统计」完整跑了一遍，47 项检查全部通过（越权项均为 403）。

## 5.7 界面优化（参照主流问卷系统重排）

### 出发点

功能齐了，但页面还是「能用的 Demo」：首页只有一列列表、所有操作平铺成一行小按钮、编辑页和统计页的信息层级是平的。我要求 AI 把六个页面按**市面上常见问卷系统**（问卷星 / 金数据 / 腾讯问卷）的信息架构重排，但**视觉必须还是原来的像素风**，不能换成 SaaS 白底卡片。

### 关键对话

> **我**：别只调颜色。看问卷星的「我的问卷」是怎么组织的——先给我指标，再给筛选，最后才是列表。现在打开首页只有一串问卷名，我得自己数有几份在收。
>
> **AI**：那前端需要一次汇总请求。建议加 `GET /api/surveys/overview` 一次返回 `surveys{total,draft,published,closed}`、`responses`、`questions`、`bank{mine,shared}`，而不是让四张卡片各发一次列表请求再自己数。
>
> **我**：可以，但列表的搜索和排序也一起补，不然指标卡只是装饰。搜索要在后端做，前端过滤只能搜到当前页。
>
> **AI**：列表接口加 `q`（标题模糊，正则元字符转义，限 60 字）与 `sort=created|updated`。注意 `overview` 路由必须注册在 `/:id` 之前，否则会被当成问卷 id 匹配掉。

> **我**：编辑页现在顶上看不出这份问卷是什么状态，我经常在已发布的问卷上改题然后吃 409。
>
> **AI**：加状态横幅，草稿黄色、已发布绿色、已关闭灰色，文案直接写「题目结构已锁定」。同时把「问卷设置」收进折叠面板——它在 90% 的情况下不用改，却占了首屏。
>
> **我**：题目列表也别一行一个大白块，题干、题型、预览、跳转规则分清楚，操作收进「更多」。

### 做了什么

| 页面 | 改动 |
| --- | --- |
| 首页 | 四张指标卡（总数 / 进行中 / 答卷 / 题库）→ 工具条（搜索 + 状态分段 + 排序 + 计数）→ 列表项主操作「编辑」+「统计」+「更多」菜单（分享与二维码、复制为草稿、导出 CSV、删除） |
| 编辑页 | 状态横幅；「问卷设置」折叠面板；题目改为紧凑行（序号 + 题干 + 题型标签 + 预览 + 单行跳转规则 + 菜单） |
| 统计页 | 四张指标卡 + 两列统计区（文本/日期题占整行）；数字题补「均值在区间中的位置」进度条与直方图坐标 |
| 填写页 | 居中卡面 + 「约 N 分钟」估算 + 进度条与题号方格 + 上一题/下一题；回退保留已填答案 |
| 题库页 | 拆成「新建」与「列表」两张卡；搜索 +「我的题目 / 共享给我的」分段；每题按主次分组 |
| 全局 | 「更多」下拉由 `app.js` 统一事件委托（点空白或 Esc 关闭），页面只写结构；≤620px 下导航横滚、统计条改两行 |

### 怎么验证的（没有只靠肉眼看）

用 Chrome DevTools Protocol 连真实浏览器，在**注入登录态之后**跑断言，而不是截图后自己看：

1. 「更多」菜单：点开有 3~4 项、标签正确、点空白处自动关闭、Esc 关闭；
2. 搜索：输入不存在关键词，断言出现空态文案而不是空白列表；
3. 分段筛选：切到「已发布」后断言行数变化与指标卡一致；
4. 填写页：1 → 2 → 回 1，断言第 1 题答案仍在；
5. 横向溢出：6 个页面 × 3 种宽度（1240 / 768 / 390）逐一断言 `scrollWidth === clientWidth`。

> **踩坑**：一开始用 `--window-size=390,844` 截图，看起来「移动端横向溢出」，查 `clientWidth` 发现是 489——Edge 有约 500px 的下限，那个溢出是假象。改用 `Emulation.setDeviceMetricsOverride({width:390, mobile:true})` 才是真实窄屏渲染，重测后溢出为 0。

### 结果

92 条测试仍全绿；六个页面在三种宽度下均无横向溢出。界面改动只涉及 `public/` 与一个新增的只读接口，未触碰任何数据模型与既有接口语义。

## 5.8 界面走查与统一（第二轮）

### 出发点

上一轮把信息架构理顺了，但仍然**像六个人各写一个页面**：有的按钮悬停会抬起、有的不动；导航当前项是黄底黑字，登录页签是蓝底白字，列表分段又是黑底黄字；删除问卷弹的是浏览器原生确认框，和整站视觉完全脱节；错误提示全靠底部轻提示，成功失败一个颜色。这一轮要求是「整体体验一遍，更流畅、更统一」。

### 关键对话

> **我**：先别加功能。把六个页面当成一条路径走一遍：登录 → 建问卷 → 加题 → 发布 → 填一份 → 看统计。哪一步让我停顿，就改哪一步。
>
> **AI**：走查下来停顿集中在三处：① 所有可点元素的状态没写全（hover 15 处、focus 2 处、disabled 1 处，而页面有 6 个）；② 选中态有三套语言；③ 原生 `confirm()` 一弹，像素风的沉浸感立刻断掉。
>
> **我**：状态统一我同意。但别加淡入淡出那套柔和动画，像素风要「硬」。
>
> **AI**：那就全部用 `steps()`：位移 70ms 两帧、悬停 100ms 两帧，视觉上是「跳」过去而不是「滑」过去。再给 `prefers-reduced-motion` 兜底。

> **我**：确认框怎么做得像这个系统？
>
> **AI**：复用 `.modal` / `.modal-box`，标题 + 说明 + 「取消 / 确定」，危险操作把确定按钮转成红字。返回 Promise，调用处写 `if (!(await App.confirm(...))) return;`。再补 Esc 取消、打开时锁滚动、关闭后焦点回到触发按钮——这三条原生 `confirm()` 本来就有，不能因为换皮丢掉。

### 做了什么

| 层 | 改动 |
| --- | --- |
| 令牌 | 颜色 / 间距 / 阴影 / 时长全部变量化，删掉写死的 `#fff4d6`、`rgba(26,28,44,.85)` 等散值；样式从「基础 + v3 + 两段补丁」合并为一套（1070 → 约 1000 行且无覆盖层） |
| 状态 | 可点元素统一「悬停抬起 1px → 按下沉入 3px → 聚焦黄描边 → 禁用降级」；补 `.busy` 加载态（宽度不跳动、防重复提交） |
| 选中态 | 导航 / 页签 / 分段统一为「黄底黑字加粗」，主色蓝只给主操作与进度 |
| 反馈 | 原生 `confirm()` → 像素确认框（5 处）；`toast(msg, 'err')` 红底白字（12 处错误提示）；弹窗入场动画 + Esc 关闭 + 滚动锁定；滚动后导航投影；空态补「下一步」按钮（首页、编辑页） |
| 流程 | 登录页自动聚焦与错误即清；填写页 Enter 进下一题、换题入场、校验失败滚到提示处；编辑页保存后跳到改动行并高亮；题库新建面板打开即聚焦题干 |
| 细节 | 六个页面补像素风 favicon（顺带消掉一次 404）；`scrollbar-gutter: stable` 避免弹窗锁滚动时页面横移 |

### 怎么确认没有改坏

沿用上一轮的 CDP 手法，但这次加了三类断言：**状态断言**（`getComputedStyle` 读主操作底色、导航选中底色、提示条底色）、**交互断言**（确认框打开后 `body.modal-open` 为真、Esc 后 promise 解析为 `false`、关闭后解锁、菜单展开后焦点进入第一项）、**回归断言**（6 页 × 3 宽度逐元素扫描 `getBoundingClientRect().right` 越界，全部为 0）。填写页的 Enter 键做了「先选题再按 Enter，断言题干变化」的正向验证，而不是只看代码。

92 条后端用例复跑仍全绿——这一轮只动 `public/`，不碰接口与数据模型。
